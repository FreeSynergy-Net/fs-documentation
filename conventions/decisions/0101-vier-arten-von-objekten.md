# 0101 – Vier Arten von Objekten: Standard-Modul, Modul-Bausatz, Anzeige-Component, Programm = Bauplan

Status: **Entwurf** (2026-11-18; Nutzer: Entscheid 6e vom 18.11.2026, Nutzer 36 = JA; Ausgestaltung Strategie; Überarbeitung nach Widerspruchsprüfung; Offen 5 entschieden 18.11.2026) · **ändert** ADR 0097 Entscheidung 3 (Fachmodul = Art 1, siehe Entscheidung 8) und das Bauplan-Schema von ADR 0099 Entscheidung 1 (Entscheidung 1: Pflichtfeld `kind` an `[[module]]`, `[[bundle]]` eigene Tabelle; `schema = 2`, Vorschlag; Entscheidung 10 unten) · **ergänzt** ADR 0098 (Entscheidung 7 „ab dem zweiten Nutzer“) · baut auf ADR 0068, 0087, 0093, 0100

**Nummer:** **0101**. Begründung: `fs-documentation` origin/main 63c30632 endet bei `0100-einstellungen.md` (angenommen); 0096 ist dort ein Entwurf (`conventions/decisions/README.md`, Tabelle); in keinem Zweig gibt es eine Nummer über 0100. Nächste freie: 0101.

**Kontext**
- Nutzer (Entscheid 6e, 18.11.2026): es gibt vier Arten von Objekten; zuerst an den **Standard** halten, erweitern nur mit **Beleg**, dass er es nicht kann; die Erweiterung wird über das Programm **fs-texts** (Bereich Standards) eingereicht; dieselbe Regel gilt für Code. Nutzer 36 = JA.
- Bestand: ADR 0097 E3: „Fachmodule ab dem ersten Nutzer, gemeinsame Module, Bausätze und Extraktion ab dem zweiten Nutzer“ (ADR 0097, Entscheidung 3); „Ausnahme = Gespräch“ (ADR 0097, Entscheidung 5; `[[exception]]` im Bauplan). ADR 0098 E7: „ein neuer Bausatz entsteht, wenn zwei **Programme** ihn brauchen; vorher bleibt das Feld ein Feld des einen Programms“ (ADR 0098, Entscheidung 7); Standard-Component je Datenart als Rückfall (ADR 0098, Entscheidung 5).
- Begriffe im Bestand: **Modul** = Laufzeit-Einheit, Stufe 1 Konfigurations-, Stufe 2 Agenten-Modul (ADR 0097, Entscheidung 3), mit Pflichten (ADR 0097, Entscheidung 3, „Pflichten jedes Moduls“). **Datenbausätze** sind keine Module: Grundtypen in `fs-types`, „keine eigene Bibliothek“ (ADR 0098, Entscheidung 1). **Fähigkeit** = Name einer Themen-Schnittstelle, die ein Katalog-Paket anbietet (ADR 0068; `0087`: Programmname nennt Fähigkeit oder Daten, Z. 6). **fs-texts** ist ein Programm (ADR 0087, Programmliste), kein Modul.
- ADR 0099 E1: Bauplan = `scaffold.toml`, `deny_unknown_fields`, `schema = 1` (ADR 0099, Entscheidung 1); `[[module]]` hat `name`, `version` (ADR 0099, Entscheidung 1); `[[exception]]` mit `talk` (ADR 0099, Entscheidung 1); unbekannter Schlüssel → abgelehnt (ADR 0099, Pflichttests). ADR 0093 Regel 1: Kanten nur von oben nach unten (ADR 0093, Entscheidung 3, Regel 1).
- Begriff „Bausatz“ (`PLAN-planungs-bausatz.md` §0 Punkt 2; `PLAN-insel-module.md`, F1): **Datenbausatz** (`kit`, ADR 0098) gegen **Modul-Bausatz** (`[[bundle]]`, Bündel mit Fassade). Beide bleiben.

**Entscheidung**
1. **Art 1, STANDARD-MODUL** = **ein Standard** plus seine **eigenen Werkzeuge**; Daten + Methoden. Nur Dinge, die der Standard beschreibt (Datenmodell, Regeln, Umrechnungen). Ein Standard darf mehrere Schreibweisen desselben Gegenstands haben: `fs-todo` = JSCalendar Task (RFC 8984) / VTODO (RFC 5545), eine Datenart (`PLAN-insel-module.md`, Zeile 1). Weitere Beispiele: `fs-jscalendar` (RFC 8984, Zeile I9), Datenbausätze Adresse/Zeitangabe/Erinnerung (ADR 0098, Entscheidung 1, Tabelle) als **Teil** eines Art-1-Inhalts (Grundtyp in `fs-types`), nicht als eigenes Modul.
2. **Art 2, MODUL-BAUSATZ** = ein **generisches Werkzeug** (Bündel mit Fassade) über eine **Schnittstelle** (Port), **nur wenn mindestens 2 PROGRAMME es brauchen** (wie ADR 0097 E3, ADR 0098 E7); vorher bleibt es Teil des Fachmoduls des einen Programms. Es kennt **keinen Programmvertrag** und keine Anzeige; Standard-**Werte** bezieht es nur von unten (`fs-types`, `fs-jscalendar`), fremde Daten nur über einen Port. Beispiel: `fs-planning` (Repo `fs-modules-planning`): **Bereitschaft** und **kritischer Pfad** gehören zum Gebiet Planung/Projektmanagement, nicht zum Standard, nicht zur UI, nicht zu den Daten. Belege: `PLAN-planungs-bausatz.md` §0 Punkt 1 (Crate `fs-planning`, Fassade `Plan`), Z. 70 (Kante auf `fs-jscalendar` erlaubt), Z. 75 („kennt keinen Programmvertrag (`tasks_v1`), sondern `fs-todo` übersetzt“); zwei Nutzer: tasks und workflows (`PLAN-insel-module.md`, Zeile 1).
   - **Name:** „Fähigkeit“ bleibt der Name der Themen-Schnittstelle (ADR 0068/0087) und wird für Art 2 **nicht** benutzt. Ein Modul-Bausatz meldet `provides` nach ADR 0068 nur, wenn er als Laufzeit-Modul (ADR 0097 E3 Stufe 2) eine Themen-Schnittstelle anbietet.
   - **Abgrenzung:** Modul-Bausatz (Bauplan-Tabelle `[[bundle]]`) = Art 2; Datenbausatz (`kit`, ADR 0098) = Speicherform, Teil von Art 1.
3. **Art 3, ANZEIGE-COMPONENT** = Darstellung eines Wertes oder einer Fähigkeit, **gebaut nach UI-Standards**: WAI-ARIA-Muster (Rolle, Zustand, Tastatur), HTML-Elemente, **W3C Design Tokens (DTCG)** für Stil, **freedesktop Icon-Namen** für Symbole. Eine Component kennt Werte über `accepts` und zeigt sie über `renders` (`fs-components-catalog`: `accepts`/`renders`/`choose`, `PLAN-angleichung-teil2-components.md`; „genauer vor allgemein“, `BEFUND-suche-allgemein-B.md:402`). Jede Datenart hat eine Standard-Component, sonst greift der Rückfall (ADR 0098, Entscheidung 5). Keine Fachlogik (ADR 0098, Entscheidung 6: `person-card` zeigt nur, was `fs-people` liefert).
4. **Art 4, PROGRAMM = BAUPLAN.** Ein Programm ist keine Code-Sammlung, sondern ein Bauplan `scaffold.toml` (ADR 0099, Entscheidung 1), der Module (Art 1, 2), Components (Art 3) und Datenbausätze zusammensteckt; Gerüst, **Standard-Frontend** und Glue werden erzeugt (ADR 0099, Entscheidung 2); handgebaute Frontend-Crates bleiben ausgenommen (ADR 0099, Entscheidung 2). Namen nach ADR 0087.
5. **REGEL (Nutzer bestätigt): zuerst an den STANDARD HALTEN.** Erweitern nur mit **BELEG**, dass der Standard es nicht kann (Fundstelle Standard + was fehlt). Die Erweiterung wird über das **Programm fs-texts** (Bereich Standards) eingereicht, nicht still im Code gelagert. Dieselbe Regel gilt für **Code**: erst Standard, dann Bibliothek, dann Eigenes.
6. **PRÜFFRAGE je neuem Code:** „Ist das Art 1, 2 oder 3?“ (Art 4 setzt nur zusammen.) Zuordnung nach **Rolle**, nicht nach Zahl der Standards: Wessen Daten sind es? Beschreibt es **Daten eines Standards** (auch in mehreren Schreibweisen derselben Datenart)? Art 1. Ist es ein **Verfahren über Daten**, das **mindestens zwei Programme** über einen Port brauchen? Art 2. Zeigt oder nimmt es nur Werte nach UI-Standard? Art 3. Teile ohne Art (z. B. Board, „objektive Aufgabe“ im Fachmodul tasks, `PLAN-angleichung.md`) bleiben im Fachmodul des Programms; im Zweifel Gespräch.
7. **Ausnahme = Gespräch, kein neues Feld:** Passt nichts, gibt es **kein neues** Ausnahme-Feld und keinen Merker „Sonderfall“. Der einzige Weg ist das **Gespräch mit dem Nutzer** (ADR 0097 E5, Antwort 128), festgehalten über das **bestehende** `[[exception]]`, das nur auf das Gesprächsprotokoll (`talk`) verweist (ADR 0099, Entscheidung 1 und Pflichttests). Keine weiteren Felder.
8. **Zwei Achsen, getrennt gehalten:** ADR 0097 E3 sagt, **wie viele Programme** etwas nutzen (Fachmodul = 1, gemeinsames Modul ab 2); Art 1/2/3 sagt, **was es ist**. Art 1/2 beschreibt den **Inhalt**, nicht die Bauform: ein Art-1/2-Modul kann ein eingebautes Crate oder ein Laufzeit-Modul (ADR 0097 E3 Stufe 1/2) sein; die Pflichten aus ADR 0097 Entscheidung 3 gelten für die Laufzeit-Form. Ein Fachmodul kann Art-1- und Art-2-Teile enthalten; „Fachmodul“ wird in 0097 E3 für Art 1 mit einem Nutzer gelesen (ändert 0097 E3, Nachtrag nötig).
9. **Beispiel-Zuordnung (belegt):**
   | Art | Beispiel | Beleg |
   |---|---|---|
   | 1 Standard-Modul | `fs-todo` (Task/VTODO), `fs-jscalendar` | `PLAN-insel-module.md`; ADR 0098, Entscheidung 1 (Tabelle) |
   | 2 Modul-Bausatz | `fs-planning` (Bereitschaft, kritischer Pfad, Rang, Fortschritt) | `PLAN-planungs-bausatz.md` §0 |
   | 3 Anzeige-Component | Blöcke in `fs-components-catalog` mit `renders`, `person-card` | `PLAN-angleichung-teil2-components.md`; ADR 0098, Entscheidung 6 |
   | 4 Programm = Bauplan | `scaffold.toml` je Programm | ADR 0099, Entscheidung 1 |
   Die Zuordnung der tasks-Insel (`PLAN-insel-module.md` §2–3) wird beim Umzug nach dieser Einteilung benannt.
10. **Schema-Form im Bauplan (ENTSCHIEDEN, 6e 18.11.2026):** Die Art steht als **Pflichtfeld `kind`** an der **gemeinsamen Tabelle `[[module]]`** (Werte: `standard` = Art 1, `toolkit` = Art 2, `component` = Art 3); keine getrennten Tabellen je Art. **`[[bundle]]`** (Bündel mit Fassade, Art 2 als Ganzes) **bleibt eine eigene Tabelle** und verweist auf seine Module. Fehlt `kind` oder ist der Wert unbekannt, wird der Bauplan abgelehnt (`deny_unknown_fields`, ADR 0099). Das ändert ADR 0099 Entscheidung 1 (`schema = 2`, Nachtrag nötig).

**Pflichttests / Prüfungen** (je ohne Umsetzung rot; Prüfungen in `fs-conformance` und Bauplan-Tabellen sind **Vorschlag**)
- `fs-conformance` (Vorschlag): jedes `[[module]]` des Bauplans trägt das Pflichtfeld `kind` (`standard`, `toolkit`, `component`); fehlt es oder ist der Wert unbekannt, ist es rot.
- Fundort-Doku-Eintrag (`data/<domain>/technical.md` bzw. Modul-Seite) **nennt die Art**; fehlt er, ist `check-docs` rot.
- Modul-Bausatz mit nur einem nutzenden Programm → rot („Teil des Fachmoduls“, ADR 0098, Entscheidung 7). Modul-Bausatz mit Abhängigkeit auf einen **Programmvertrag** (`tasks_v1` o. ä.) oder ein Programm-Repo → rot (Seiten- bzw. Aufwärtskante, ADR 0093 Regel 1; `PLAN-planungs-bausatz.md`). **Standardkenntnis ist erlaubt** (Abhängigkeit auf `fs-jscalendar` und andere Standard-Module nach unten); verboten ist nur die Seitenkante.
- Component mit Fachlogik oder ohne UI-Standard-Beleg (ARIA-Muster, DTCG-Token, Icon-Name) → rot.
- Erweiterung eines Standards im Code ohne Beleg-Eintrag (Standard-Fundstelle + „kann nicht“) → rot; Einreichung über fs-texts muss im Beleg verlinkt sein.
- Neuer Code ohne Art und ohne Gesprächsprotokoll (`[[exception]]` mit `talk`, ADR 0097 E5) → rot. Kein neues Ausnahme-Feld: Bauplan mit unbekanntem Schlüssel wird abgelehnt (ADR 0099, Pflichttests).

**Folgen**
- ADR 0097: Nachtrag zu E3 (zwei Achsen, Entscheidung 8). ADR 0098: Entscheidung 7 gilt für Art 2 gleich. ADR 0099: Nachtrag zu E1 (Pflichtfeld `kind` an `[[module]]`, `[[bundle]]` eigene Tabelle, `schema = 2`).
- fs-release: Workflows `vorhandenes-zuerst` und `modul-bausatz-neu` fragen die Prüffrage; `fs-blueprint` kennt `[[module]]` (Art 1), `[[bundle]]` (Art 2), `[[component]]` (Art 3) (Vorschlag; `PLAN-planungs-bausatz.md`).
- fs-conformance: Prüfung „`kind` je Modul“ (Vorschlag); `check-docs` prüft den Fundort-Eintrag.
- fs-texts (Programm): Einreichungs-Weg „Standard-Erweiterung“ (Fundstelle, Beleg, Status); Workflow dafür.
- Umzug der tasks-Insel (`PLAN-insel-module.md`): Teile werden Art 1 (`fs-todo`, Datenbausätze) oder Art 2 (`fs-planning`) genannt; Kreis-Risiko `fs-people` siehe `PLAN-planungs-bausatz.md` §0 Punkt 4.

**English summary.** Draft ADR 0101 (number confirmed: origin/main ends at 0100) defines four kinds of objects: (1) standard module = one standard plus its own tools (data + methods; e.g. fs-todo, which covers two notations of one data kind); (2) module kit (Modul-Bausatz) = a generic tool behind a port, only when at least two programs need it (e.g. fs-planning); it may depend on standard modules but not on a program contract; "capability" stays the name of the topic interface (ADR 0068/0087); (3) display component built to UI standards (WAI-ARIA, HTML, W3C DTCG, freedesktop icon names); (4) a program is a blueprint (scaffold.toml). Rule: stick to the standard first; extend only with proof, submitted through the program fs-texts; same for code. Test question: whose data, which programs use it? If nothing fits, talk to the owner; `[[exception]]` only points to the talk record, no new fields. The blueprint schema form is decided: a mandatory `kind` field on a shared `[[module]]` table, while `[[bundle]]` stays its own table. It changes ADR 0097 E3 and the ADR 0099 blueprint schema.
